## A5: start delay

Taps on the same related video (`CDkaJYJlk90` from `kJQP7kiw5Fk`), fresh page each time:

| Mode | Start |
|---|---|
| Shield off, no ad scheduled | 0.7–0.9 s |
| Shield off, ad scheduled | pre-roll plays, content after ~22 s |
| JSON pruning only | 5.2–6.2 s |
| Network blocking only | pre-roll plays |
| Full shield | 5.7–6.9 s |

Correlation over 10 full-shield taps: pre-roll in the raw response (`adSlots` with
`playerBytesAdLayoutRenderer`) → 5.4–6.1 s (7 of 7); no pre-roll → 0.76–1.1 s (3 of 3).

Mechanism, from decoding the SABR responses (`ump.mjs`): the first `videoplayback` POST returns
105 bytes with no media, only a SABR context update (part 57) and a next-request policy (part 35)
with a **4000 ms backoff**. The player waits, asks again, and gets media at ~6 s.

Tried and rejected:
- **Dropping the backoff** from the response (CDP response rewrite): the player retries at once,
  the server keeps answering with backoffs and no media; starts got worse (7–17 s).
- **Keeping the pre-roll and fast-forwarding it** (the fallback skipper): 13–22 s, because SABR
  serves the ad at the server's pace.

So stripping the pre-roll, as now, is the fastest option found. The full-page-load intents used
for A1 never got a pre-roll scheduled, which is why that path measured ~2 s.

## F: autoplay while hidden

Cause: `shield.js` called `player.nextVideo()` first and used the URL captured from the watch-next
response only as a fallback. On m.youtube.com the player does not know the playlist
(`getPlaylist()` returns `[]`, `getPlaylistIndex()` -1), so `nextVideo()` went to an unrelated
suggestion and dropped `list=`. Also, `inPlaylist` was false for mixes: the mobile site puts the
queue in `singleColumnWatchNextResults.playlist.playlist`, not `playlistPanelRenderer`, and the
next item was looked up with `currentIndex`, which is the position in the whole playlist rather
than in `contents`.

Fix (`shield.js`): advance to the captured next video directly (`nextVideo()` only when nothing was
captured); read the mobile `playlist` object; find the current video in `contents` by id.
Tests: `shield.test.mjs` now mocks the mobile response shape and a `nextVideo()` that behaves like
the real one. 60 passed; the previous `shield.js` fails 5 of them.

After the fix: F1 `kJQP7kiw5Fk` (mix RD…) → `DtGg5ltlVvM` in the mix; F2 `9bZkp7q19f0` → mix item
2; F3 `kPa7bsKwL-c` → `u2ah9tWTkmk` in the playlist; all playing on their own.
